# 性能优化与丢包边界

## 0.1.5 优化范围

目标是降低逐包 CPU／分配开销和安装资源需求，而不是删掉协议校验或通过截包来制造“低丢包”。保持原有 HTTP PCAP、完整 Ethernet 帧、自动 LAN、首包立即进入上传、有界队列和离线不重放。

1. **只解析一次自身连接**：保留最多 128 条连接记录，改用有界索引查询双向 TCP tuple。IPv4 非首分片和 IPv6 Fragment header 的原始排除语义仍保留。旧连接记录不会立即清理，避免仍在采集管道中的自身包反馈。
2. **有界 record 缓存**：复用常见尺寸的 PCAP record，最多缓存 256 KiB。仅在整个上传写入消费完成后回收，队列必须持有包的独立副本；不为每个槽位预分配 65535 字节。
3. **32 KiB 读取缓冲**：合并读取已经到达管道的数据，不等填满、不延迟首包、不改变时间戳或完整帧。
4. **单架构安装包**：只带目标架构，降低压缩包／解包的 `/tmp` 占用；运行功能和依赖与通用包相同。安装包变小不代表进程 RAM 按相同比例下降。

缓存减少稳态分配次数，但增加有限的缓冲保留内存；不承诺所有负载下峰值 RAM 都更低。HTTP/TLS 安全、状态权限、停止确认和服务端最终包数校验不应为“精简”而删除。

## 队列为什么不能只看 4 MiB

队列同时限制 **512 包**和 **4 MiB PCAP record 数据**。对于 60-byte 帧，512 包只占 38 KiB；对于 1500-byte 帧，约 758 KiB。常见小包先碰到包数限制，不是字节限制。

假设持续捕获 100 Mbit/s 的帧字节、上传完全停顿（不含链路和 PCAP 开销），这些包数分别只覆盖约 2.46 ms 和 61.44 ms。该计算不是路由器吞吐测试。扩大队列只可能缓解短时突发，会增加 RAM、排队延迟和陈旧流量，不能解决持续拥塞。

## “丢包”有多层

- **网卡／驱动／内核漏采**：目前状态接口不统计所有这些丢包，不能用页面 `dropped=0` 证明零丢包。
- **应用队列溢出**：消费者跟不上或网络写入停顿，达到队列上限。
- **离线丢弃**：尚未完成认证／连接或正在重连时，捕获的副本立即丢弃并计数，这是低延迟实时策略。
- **链路或接收端问题**：写入本地 HTTP 流不等于实时收到最终确认。正常上传结束会核对接收端最终包数；异常中断可能没有最终确认。
- **未经过接口／硬件加速旁路**：不是应用队列丢包，修改用户态程序无法恢复未观察到的帧。

LAN 待发送流量持续超过实际上传／服务端处理能力时，不存在仅靠低端发送端实现的零丢包方案。0.1.5 不加游戏分类器，不等待识别，也不擅自过滤未知协议、只发 UDP、减少 snaplen 或移除自身连接排除。

## 验证与性能测量

```sh
go test -count=1 ./...
go vet ./...
node tests/ui.cjs
python tools/build.py
python -m unittest discover -s tests -p test_packages.py -v
go test -run '^$' -bench . -benchmem ./internal/sender
```

合成 benchmark 只用于比较同一环境下的实现；Windows x64 和内存 reader 结果不能换算成软路由 CPU 降幅或实际丢包百分比。`bufio.Reader` 的底层调用减少也不等于同等比例的吞吐提升。Linux CI 验证首包不等待后续包、完整性、重连、并发、安装／回滚／卸载，并用真实 tcpdump 和合成 Ethernet 帧核对本地接收端最终计数。

实机验收建议保持同一设备、固件、通道和流量，仅更换发送端版本，分别记录 CPU、进程 RSS、捕获速率、丢包计数、重连次数和接收端计数。没有实机数据时，不承诺最低 RAM／CPU 或任意速率下零丢包。
